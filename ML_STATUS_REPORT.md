## TL;DR (facts that matter most)

1. **All BTC/ETH/SOL data is synthetic.** The README says "Geometric Brownian Motion". Statistical tests agree (§1). The WBTC CSVs look like real BTC data but their provenance is undocumented.
2. **Plan v2 is only partly implemented.**

   | Plan item | Status |
   |---|---|
   | Step 0 | done |
   | Phase 1 (DirectionClassifier) | built and trained, **not served by the API** |
   | Phase 2 (RegimeDetector) | **not started** |
   | Phase 3 (unified `generate_signal`) | **not started** |
   | Phase 4 (walk-forward backtest) | **not started** |
   | Phase 5 (calibration) | **not started** (attribute declared, never computed) |
   | Phase 6 (API schema update) | **not started** |
   | Phase 7 | conditional, correctly not started |

3. **A different signal function exists.** `training/wbtc_signal.py::generate_signal` is WBTC-only and its logic, thresholds and risk direction differ from the plan. The API's live signal is the old `STRONG_BUY/STRONG_SELL/UNCERTAIN` inline code (duplicated twice in `prediction_service.py`).
4. **The DirectionClassifier has no predictive skill on held-out data.**
   - Test ROC-AUC 0.52–0.54 and MCC 0.04–0.10 [audit-computed].
   - Test accuracy is below the test-set majority-class baseline for all 3 assets.
   - For BTC, the class predicted as DOWN had a *higher* mean forward return than the class predicted as UP.
5. **The only backtest that exists is invalid.**
   - `lightweight_backtest.py` runs on 386 hourly rows spanning 16 days, with overlapping 30-day returns summed.
   - It reports Sharpe = 299.1, buy-and-hold = −100%, hit rate = 100% on 10 trades.
   - No `{asset}_backtest_report.json` exists. `GET /backtest/{asset}` returns 404.
6. **The API has live defects.**
   - BTC fails to load under `uvicorn` (pickle saved as `__main__.RiskClassifier`).
   - The BTC/ETH LSTM report stores a *price* in the `prediction_30d` field. This corrupts `agreement`, `signal` and `ensemble_price`.
   - `/metrics/{asset}` serves hand-typed numbers that appear in no artifact.
7. **ETH and SOL risk classifiers are stale.** They were trained with the old composite-score labelling, which was a function of the input features. The code was changed on 2026-08-27 and only BTC was retrained. Their reported 79% accuracy is circular.

## 3. LEAKAGE AND VALIDITY AUDIT

**a. Does the backtest evaluate on data the model was trained on?**

- There is no BTC/ETH/SOL backtest, so it cannot be answered for them. The plan's walk-forward backtest uses the full-history artifacts. The BTC/ETH/SOL direction artifacts are trained on 2024-01-31 → 2025-06-19. A backtest over the full 2024-2025 range would be in-sample for ~72% of the data.
- WBTC (`lightweight_backtest.py`)
  - It evaluates on `wbtc_test_model.csv` (2025-11-15 → 2025-12-01). The classifier was fit on train and evaluated on val (`fit_presplit`), not on test.
  - Label-horizon leakage remains. A 30-day forward label implies train labels extend to 2025-11-29 20:00, which overlaps the validation features (starting 2025-10-30 21:00). Val labels extend to 2025-12-15, which overlaps the test features (starting 2025-11-15 22:00). **No embargo exists between the pre-split CSVs.** `fit_presplit` explicitly skips the embargo (docstring lines 414-420).
  - Even though test rows were not trained on, train-set labels depend on prices in the val period, and val labels depend on prices in the test period.
  - The StandardScaler appears to have been fit on the training block (train means are exactly 0.0000; val/test are not). The scaler itself is not available.

**b. Overlapping steps vs. a 720h horizon; Sharpe annualisation; overlap handling**

- WBTC lightweight backtest
  - Step is 1 hour, horizon is 720 hours. Adjacent rows share 719/720 of their forward return window. 386 rows ≈ 0.54 independent windows.
  - Per-row strategy returns are *summed* (`strategy_return.sum()`, line 149). Buy-and-hold = `exp(sum of 386 overlapping 30d log-returns) − 1` = −100.00%, a meaningless number.
  - Sharpe = `mean/std * sqrt(8760)` (line 154), computed on non-HOLD rows only. 8760 is hours per year, applied to 30-day returns sampled hourly. The result is 299.1.
  - **No overlap handling exists** (no non-overlapping sampling, no HAC/Newey-West, no block bootstrap).
- Plan Phase 4 specified 24h steps with `sqrt(252)` (`PLAN.md:495`). That has never been built. Crypto trades 365 days a year, so the plan's `sqrt(252)` is itself questionable. 24h steps against a 720h horizon would still overlap 29/30.
- `/risk` Sharpe (`classifier.py:518-553`)
  - It is `mean(return_1d)/std(return_1d) * sqrt(252)`, where `return_1d` is the 24h log-return **sampled every hour** (overlapping).
  - It is computed over the entire history including training data.
  - The factor is 252 where 365 would be appropriate for 24/7 markets.

**c. Were thresholds tuned using backtest results?**

- **Regime thresholds:** not applicable; no regime detector.
- **Direction thresholds** (P40-based): derived from training labels only (`direction_classifier.py:277`), not from backtest results. Correct per plan.
- **Risk gate / direction threshold (plan 0.60 / 50):** not implemented anywhere. The WBTC defaults are 0.50 / 0.50 / 70 (`wbtc_signal.py:5-7`).
  - There is one commit for that file and no commit message or comment says how 0.50/70 were chosen.
  - Whether they were tuned against the test split is **UNCLEAR**.
  - The CLI exposes `--up-thresh/--down-thresh/--risk-thresh`, so sweeping is possible.
  - The backtest file header calls the test split "never used during training or threshold decisions" (line 68). That claim cannot be verified.
- The comment at `lightweight_backtest.py:68` also does not hold for labels (see 3a).

**d. Does any feature use future information?**

Checked in `features/feature_engineering.py` (92-164):

| Feature | Verdict |
|---|---|
| `return_1h/1d/7d/30d` = `ln(p_t / p_{t−n})` | Backward-looking. No leakage. |
| `volatility_14d` (rolling std of `return_1h`, window 336, `min_periods` = 336) | Backward-looking, includes t. No leakage. |
| `ma_7d`, `ma_30d` (rolling mean, includes the current bar) | Backward. |
| `ma_cross` ∈ {−1, 0, +1} | Matches the plan's description (lines 144-149) and uses only t and earlier. |
| `volume_change_pct` (`pct_change(1)`) | Backward. |

- Labels use the reverse-rolling trick (`direction_classifier.py:791-797`): `price_{t+720}` for direction and `std(r_{t+1..t+168})` for risk. They are forward-looking by design and live only in `fit()`.
- A feature/label boundary check passes: row t's features never include t+1 or later.
- **Prophet regressors** (`forecaster.py:108`): `volatility_14d`, `ma_cross`, `volume_change_pct`, daily-median aggregated. The future values of these regressors are filled with the last known value (`_build_future_df`, 378-400), which is not leakage but a flat-regressor assumption.
- **WBTC:** features are pre-scaled; scaler fit data is not available. Not verifiable.

**e. Is the Prophet forecaster used inside the backtest (`derive_trend_from_forecaster`)? Fit only on data before t?**

- No such function exists. There is no walk-forward backtest.
- The WBTC backtest uses `return_30d` for "trend" (trailing). The Prophet model is not used.
- For the *served* signal: Prophet is fit once on the full history to 2025-12-31 and no refit occurs at inference. If Phase 4 were implemented as written, it would call the one pre-fitted full-history Prophet at every historical `t`. That would **leak** all future data (Prophet saw the whole series), and it is not re-fit on `iloc[:t]`. The plan text (`PLAN.md:447-451`) states models are not re-fit at each step, which would not apply to the Prophet used for `trend`.

**f. Baselines**

- Computed in code: only the WBTC *accuracy* baseline in `fit_presplit` (majority class, lines 528-550) and the buy-and-hold figure in the WBTC backtest. The WBTC accuracy baseline shows the model does **not** beat majority (0.714 vs 0.800).
- Not computed anywhere: last-value, always-HOLD (trivially 0), random, bootstrap CI.
- Audit-computed (see 2.2): on held-out test splits the model does **not** beat the majority-class baseline for any of BTC (0.572 vs 0.720), ETH (0.297 vs 0.534) or SOL (0.242 vs 0.507).
- Price-forecast skill vs last-value baseline: **[not available]** (no metrics exist).
- WBTC backtest hit-rate baseline: 91.7% of test rows have `target_return_30d < 0` [audit-computed]. A SELL hit rate of 100% on 10 trades is therefore nearly the base rate (random SELL would hit 91.7%).

**Additional validity findings:**

- WBTC hit-rate definition (`lightweight_backtest.py:138-146`) uses the sign of `target_return_30d`, not the classifier's label. In the test split every row is FLAT by the label rule (|return| < 0.1563), so the classifier's task is degenerate on test.
- The WBTC risk proxy `rank(pct=True)` over the whole test set (line 79) uses future test values (look-ahead).
- Whole-series regime shifts: train/val/test mixes are totally different (§2.2, §1.3). Results are dominated by which regime lands in the test window.

## 7. NFT / EXTENSIBILITY

**Where the asset list is hard-coded (`btc/eth/sol`)**
- `api/prediction_service.py:97` `SUPPORTED_ASSETS = ["btc","eth","sol"]`.
  - Used for startup load (405), `/health`, `/assets`, and validation in every route (525, 684, 730, 812, 882, 986, 1104).
- `MODEL_METRICS` keyed by btc/eth/sol (103-185). Accessing `MODEL_METRICS[asset_lower]` (line 690) would raise `KeyError`/500 for any new asset that passes validation.
- CLI `choices=["btc","eth","sol"]` in `training/train.py:465`, `models/direction_classifier.py:879`, `features/feature_engineering.py:377`.
- `data/phase0_distribution_analysis.py:159` `assets = ["btc","eth","sol"]`.
- `models/direction_classifier.py:161` `PHASE0_THRESHOLDS` (btc/eth/sol).
- `shared/mock_data.py:8` (backend; BTC/ETH only). `backend/controllers/aai_controller.py` normalisation bounds (BTC/ETH only).

**What would have to change to add a new asset**
1. Data loader: `load_raw_csv` (feature_engineering.py:243) assumes `ml/data/raw/{asset}_prices.csv` with columns `asset, price, volume, timestamp`, hourly, with price > 0 (`_validate_input` 335 rejects ≤ 0). All windows assume hourly spacing (W_1D = 24, etc.).
2. Replace the three hard-coded lists and CLI `choices` with one registry/config (or discover from `ml/data/raw`).
3. Artifact naming is already `{asset}_*.pkl` (prophet, rf_classifier, direction_clf, lstm). New assets work if the names are `[a-z0-9]+`.
4. API validation: the path param is lower-cased and checked against the list. Both the metrics and `ModelCache` would need dynamic entries.
5. Frozen `MODEL_METRICS` should be replaced by reading report JSONs (which currently contain no metrics).

**What an NFT collection would additionally need**
- A different data model. Collections have floor price, sales volume and sparse/irregular timestamps. The current code assumes a gap-free hourly series with a continuous price and 30-day = 720 rows. Daily or irregular data would require re-parameterising the window constants in `feature_engineering.py` (73-80) and `FORWARD_HORIZON_HOURS` in both classifiers.
- Illiquidity and wash-trade handling, and no 24/7 continuous quote. Features such as `volume_change_pct` (hourly) and `ma_cross` have no NFT-specific analogue.
- A real ingestion path: none exists today (§1.4).
- The WBTC pipeline shows one existing precedent for a "bring-your-own-split CSV" path (`fit_presplit`). It skips embargo and CV, so it is not a safe template for a new asset class.
