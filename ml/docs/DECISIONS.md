# DECISIONS (append only; don't re-debate without a new reason)

| # | Decision | Why |
|---|---|---|
| D1 | Restart as ml-v2; v1 archived at tag archive/ml-v1 | v1 used synthetic data; 3 signal functions; stale artifacts |
| D2 | Real data only (Binance public klines) | v1 metrics were meaningless on GBM data |
| D3 | Daily bars, horizon = 30 rows | Matches Murray 2023 and McNally 2016; avoids v1's "30 days = 30 hours" bug. Hourly may return later for risk only. |
| D4 | Assets: BTC, ETH, SOL; WBTC dropped for now | WBTC tracks BTC; v1 WBTC data was scaled, gapped, unsourced |
| D5 | ML owns only /predict and /risk | AAI is backend |
| D6 | No extra top-level response fields | CONTRACT has additionalProperties:false; extras go to /debug |
| D7 | signal values BUY/HOLD/SELL/UNCERTAIN first | Direction accuracy expected near 50-55%; STRONG_* needs evidence |
| D8 | Ensembling only if it beats the best single model on validation | Murray 2023: averaging with weaker models hurt |
| D9 | Risk = forward 30d realised vol terciles (thresholds from train), score = 100 - P(high)*100 | Forward-looking, no circularity with features |
| D10 | Training uses downloaded historical files; live fetching comes later | User decision |
| D11 | config.py stores split FRACTIONS (0.70/0.15/0.15), not dates; dates are derived per asset and written to metadata.json | Assets start on different dates (SOL 2020 vs BTC 2017); fixed dates would give SOL a tiny train set |
| D12 | Repo root is the working directory; `ml` is a package (`ml/__init__.py`); tests run as `python -m pytest ml` | Matches `python -m ml.x.y` (AGENTS rule 9); avoids collecting other teams' tests |
| D13 | Only `ml/data/raw/` is git-ignored, not `ml/data/` | DATA.md requires fetch.py/validate.py to be tracked; v1's `ml/data/` rule would have ignored them |
| D14 | Python 3.10-3.12 supported; dev machine runs 3.12.10 | scikit-learn/FastAPI fine on 3.12; TensorFlow/Prophet optional, only if they beat baselines |
| D15 | Validation reports tracked at ml/reports/data/{asset}_validation.json; data/raw/ stays ignored | Small files, and they are the evidence the data is real |
| D16 | Split boundaries from 70/15/15 of the full series (n rows): b1=floor(0.70n), b2=floor(0.85n). train=[0, b1-30), validation=[b1, b2-30), test=[b2, n). The last 30 rows of the series have no forward label and are excluded from labelled data | Embargo cut from the end of the earlier split, so test ends at the latest data |
| D17 | Embargo rule as recorded in D16 is accepted: validation and labelled test each have about 0.15n-30 rows; only the test date range is exact | User confirmation of D16 (2026-10-18) |
| D18 | n for split boundaries = number of rows AFTER dropping the 30 warm-up rows; b1=floor(0.70n), b2=floor(0.85n); train [0,b1-30), validation [b1,b2-30), test [b2,n); the last 30 rows have no label and are excluded from labelled data | Splits are made on the feature table, which starts after the warm-up; refines D16's definition of n (user decision, 2026-10-19) |
| D19 | Direction threshold = 40th percentile of \|fwd_return_30d\| on TRAIN only; risk class thresholds = 33rd/67th percentiles of fwd_vol_30d on TRAIN only; thresholds are stored in metadata, never recomputed on validation or test | Thresholds from later data would leak the future into the labels (user decision, 2026-10-19) |
| D20 | Evaluation context: validation and test are dominated by FLAT and low-risk classes (see *_dataset_summary.json). Therefore: (1) the majority-class baseline uses the TRAIN majority; (2) every classification report includes balanced accuracy and macro-F1 next to accuracy; (3) risk is also evaluated as ranking via Spearman correlation against continuous fwd_vol_30d; (4) every report includes n_labelled and n_effective = n_labelled / 30 | Plain accuracy is misleading on unbalanced classes, and daily rows with a 30-day horizon overlap, so they are far from independent (user decision, 2026-10-19) |
| D21 | Model evaluation uses expanding-window walk-forward over rows [0, b2-30) (train+validation together). The test split [b2, n) is sealed: the harness raises if asked for any test row, and it is evaluated once at the end. First origin after MIN_TRAIN_ROWS=730 rows; step = 30 rows (retrain every 30 days). At origin t, the fold trains on rows i < t-30 (embargo = horizon) and predicts rows [t, t+30). Thresholds (D19) and baseline parameters are refit per fold from that fold's train rows only; evaluation labels use that fold's thresholds. Results are pooled across folds and reported with n_folds, n_pooled, n_effective = n_pooled/30, and the same metrics on every 30th pooled row | One validation split has n_effective of only 10-16 (D20); walk-forward uses all pre-test history while every prediction stays out-of-sample (user decision, 2026-10-19). Implementation: first origin = MIN_TRAIN_ROWS + 30, so the first fold trains on exactly 730 rows; the last fold is cut at b2-30 and may be shorter than 30 rows |
| D22 | Model selection: each model type gets a small pre-declared set of configurations, recorded with their count. Selection rule (fixed before any model runs): a model is approved only if it beats the best baseline on the pooled walk-forward metric AND a paired moving-block-bootstrap 95% CI of the difference excludes 0. The test split is touched once, after the final choice | Prevents choosing among many configurations by luck and keeps test untouched (user decision, 2026-10-19) |
| D23 | The test split has been partially seen: Phase 3 baselines.json contains test-split metrics and the test class balance is known. No threshold, model or selection was tuned on it. Final claim: test was never used for selection | Honest record of what has been looked at (user decision, 2026-10-19) |
| D24 | Risk model: target is log(fwd_vol_30d) (regression). Output is predicted log-vol. Mapping to the 0-100 risk_score is deferred to Phase 5/6 and needs its own D-number. Class metrics use each fold's own thresholds applied to the prediction, so they are comparable to the persistence baseline | Vol is skewed; log makes it closer to symmetric. Refines D9: a regression gives no P(high), so D9's score formula cannot be used until that new D-number exists (user decision, 2026-10-19) |
| D25 | Model approval protocol (refines D22): candidate configs are declared in code before any run, max 4 per model type, and the count is recorded in the report. Folds are split chronologically: configs are ranked on the first 60% of folds; the top config is then confirmed on the last 40% with a paired block-bootstrap 95% CI of the difference in Spearman vs persistence. Approved only if the CI excludes 0 and the point estimate is positive. All configs' results are reported, not only the winner | Ranking and confirming on separate folds stops the winner being chosen and judged on the same data (user decision, 2026-10-19). Implementation: ranking uses pooled Spearman on the first floor(0.6 x n_folds) folds |
| D26 | Phase naming: 4a = risk model, 4b = price model, 4c = direction model (PLAN.md table renamed) | Risk is built first; the earlier PLAN listed price as 4a (user decision, 2026-10-19) |
