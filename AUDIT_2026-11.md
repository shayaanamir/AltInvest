# AltInvest: production-readiness audit (2026-11)

- **Scope:** the whole repo at branch `phase-7-integration` @ `c59ad96`, working tree clean.
- **Date:** 2026-11-02.
- **Method:** read-only. Four parallel audit tracks (frontend; backend + DB + security; pipelines; infra + live end-to-end run), merged here. The lead auditor re-checked every P0/P1 against the code.
- **Labels:**
  - **VERIFIED** means it was run (tests, lint, build, a live local stack driven over HTTP, an in-memory app probe), or the code path was traced end to end.
  - **INFERRED** means it comes from reading code only.
  - Docs, STATUS files and commit messages were never accepted as evidence.
- **Data safety:**
  - No command touched the shared Atlas cluster.
  - The live stack ran under a separate compose project (`altinvest-audit`), with `MONGO_URI=mongodb://mongodb:27017` checked in `docker compose config` and inside the container *before* the backend started.
  - SMTP was unset. `CMC_API_KEY` was not passed.
  - Seeds and test fixtures were written only to that throwaway local container.
  - The stack, volumes and images were removed afterwards (`down -v`, `rmi`). The user's own containers were not touched.

Status legend: ✅ built and working (verified) · 🟡 partial · 🎭 mocked, seeded or fake but looks real · ❌ not built · 💥 broken.
Severity: **P0** blocks a working end-to-end product, or is a security or data-loss risk. **P1** must be fixed before real users. **P2** should be fixed. **P3** nice to have. Effort: S (≤1 day), M (a few days), L (≥1 week).

## 1. Executive summary

**Verdict: not production-ready. About 35%.**

What is solid:
- The application shell, auth, sessions, per-user CRUD, ownership isolation, and the frontend↔backend wiring. All 67 frontend calls match real routes, and the live two-user test found no way for one user to reach another's data.
- The ML service: honest, contract-validated, UTC-correct.

What is wrong is the core value of the product, the data:
- **No live market data exists.** Every price, 24h change, portfolio value, P&L, chart, trending score and snapshot comes from a one-off seed script, and the hourly price history is synthetic random-walk data.
- 15 of 18 assets show invented "model forecasts" and risk scores, so their AAI and BUY/SELL badges are built on fabricated inputs.
- NFTs and the insights feed are seeded, and some of it is fictional, including made-up headlines credited to real outlets.
- Nothing in the API or UI marks any of this as seeded.
- A fresh deployment is an empty app.

On top of that there are real security gaps, there is no production deployment path, and there are almost no tests outside ML.

## 4. Feature inventory

**Built and ready (verified)**
- Signup, login, rate limiting, server-side sessions (list, revoke, revoke others), logout revocation, change password (signs out other sessions), verify email and resend, forgot-password with an identical response for unknown emails.
- Ownership isolation on every user-scoped endpoint, Pydantic validation, and no NoSQL-injection paths.
- Watchlists: full CRUD.
- Notifications: full CRUD and unread count.
- Portfolio holdings: maths (merge, weighted average, sell, realised P&L, remove transaction).
- Alerts: rule definition and validation, and trigger history.
- FX from Frankfurter (every 6 h) and client-side currency conversion.
- ML service for BTC/ETH/SOL: refresh, validation, serving, contract checks, backend pull at 00:15 UTC, stale note.
- Live sentiment pipeline: RSS + VADER/FinBERT, every 15 minutes, with a cross-process lock.
- Frontend↔backend API wiring (67/67 match), error boundaries, connection banner, toasts.
- Frontend production image (builds, client-side routing fallback works), but not wired into anything.

**Partial 🟡**
- **Alerts:** evaluation works, but price alerts can't fire, sentiment alerts can fire falsely, push is not built, and email has no retry.
- **Dashboard and Portfolio:** these work, but on frozen prices.
- **Asset Detail:** real for the ML/sentiment parts, seeded for the rest.
- **AAI:** the computation is right, but inputs are seeded or stale, it is inconsistent across endpoints, and sentiment is stored on two scales.
- **Portfolio snapshots:** the job runs, but values frozen prices, so the chart is flat.
- **Settings:** security, appearance and preferences work; notification preferences and dashboard layout do not.
- **Profile:** writes an unchosen `risk_profile`.
- **Export:** client-side only, from stale data.
- **Token refresh:** sliding JWT only, no rotation.
- **Discover:** the risk filter is inverted.
- **Health endpoint:** static.

**Mocked, seeded or fake but looks real 🎭**
- Prices, market caps, 24h changes and volume (seed snapshot), and hourly price history (synthetic random walk).
- Predictions and risk for 15 of 18 assets (`seed-v1`).
- `risk_breakdown` for **all** assets, including BTC/ETH/SOL.
- AAI rows for ARB, DAI and BASE (never refreshed).
- NFT collections, tokens and sales, partly fictional ("Neon Drifters" and others).
- Market insights: fabricated headlines credited to CoinDesk, Decrypt, The Block and MarketWatch.
- Sentiment themes.
- Backfilled snapshots (the `source` marker is dropped).
- The "Live Markets" ticker on Login and Signup.
- `routes/risk.py`, which returns `shared/mock_data` values when a row is missing **or Mongo throws**.
- Onboarding.
- Notification channels, quiet hours and alert types.
- "Push" delivery.
- A 50/100 sentiment shown when there are no readings.
- "Hold" invented for unscored holdings.

**Not built ❌**
- Market-data ingestion.
- Asset catalogue bootstrap without seeds.
- Onboarding persistence and gate.
- Server-side data export.
- NFT detail page (the backend `/nft/*` API exists but nothing uses it).
- Global transaction-history view.
- Push notifications.
- 2FA and OAuth (the UI is honest about these).
- Refresh-token rotation.
- Production compose, backend production image, CI.
- Frontend tests.
- Sentiment-engine tests (the files are empty).
- Email-change flow.
- ML PLAN_NEXT A1–A7 and D1 (§7.3).

**Broken 💥**
- Password-reset single use and revoking sessions on reset.
- Fresh deployment without seeds.
- `/assets/{s}/intelligence` AAI cache (never hits).
- `useAsync` stuck loading (6 panels).
- The `max_risk` filter.
- The sentiment fallback scale (0–100 read as −1..1).
- `/health` while the DB is down.
- A quantity of `Infinity` returns 500.

**Shared shell findings (VERIFIED unless marked)**
- **Sidebar** is a `<div onClick>` with no role or tabIndex, so it can't be used from the keyboard. It is a fixed 230 px with no viewport breakpoint and the shell hides overflow, so the app is unusable on phones (INFERRED, not rendered).
- **Topbar search** has a proper ARIA combobox. Insight results are opened with `window.open(item.url)` with no scheme check (`TopbarSearch.jsx:118`).
- **ConnectionBanner** is driven by `connectionStatus.js`. Timeouts are reported as "unreachable", which together with the poller timeout produces false offline banners. `systemStates.json` says "showing the last data we had", but there is no offline cache.
- **ErrorBoundary ×2:** `components/shared/ErrorBoundary.jsx` is a 2-line re-export, so remove it. The page boundary is keyed on `pathname|fx`, so every navigation or currency change remounts the whole page.
- **ToggleSwitch ×2:** byte-identical except for the CSS prefix, and callers pass no `label`, so the switches have no accessible name.
- **Toasts:** fine (`aria-live`).
- **No modal has a focus trap.** Several have no `role=dialog`.
- **Unused dependencies:** `three`, `@react-three/*`, `radix-ui`, `shadcn` (a CLI), `lucide-react`, `motion`, `clsx`, `tailwind-merge`, `cva`, and Geist. Tailwind v4 is configured with v3 directives that produce nothing.

### 6.5 Module improvement items (IMPROVEMENT)
- **IMP-B01 Worker container:** move all 7 schedulers and FinBERT into one `worker` service (APScheduler plus a Mongo lease lock), leaving a stateless API. This removes the duplicate-job class of bugs, lets the API scale, and takes torch out of the API image.
- **IMP-B02 Settings object:** one `pydantic-settings` object validated at startup (required URI, DB name, `JWT_SECRET` of 32+ bytes outside dev, `APP_ENV`, CORS origins). Replaces scattered `os.getenv` calls and the accidental `.env` discovery.
- **IMP-B03 One Mongo client:** a single shared `MongoClient(tz_aware=True, timeouts)` for both the backend and the sentiment engine, and one DB. Removes the hand-written naive-datetime patches throughout.
- **IMP-B04 Tokens:** a short-lived access JWT plus a rotating, hashed refresh token in an httpOnly SameSite cookie, with reuse detection.
- **IMP-B05 Mail outbox:** send mail through an outbox collection with a retrying sender. Fixes the timing leak, the blocked request threads and the lost emails.
- **IMP-B06 Provenance:** a uniform `source` / `as_of` / `model_version` / `is_demo` on every derived number.
- **IMP-B07 Universe cache:** a 30–60 s TTL cache on the universe endpoints, which currently run about 8 aggregations per request.

### 7.1 A. Market data (CMC) → storage → Discover / Detail / Portfolio
- **Flow (VERIFIED):** none. The backend's only outbound HTTP calls are the ML pull and FX.
  - `asset_market_data` is written only by `db/seed_assets.py:134`, from a static JSON snapshot.
  - `prices` is written only by `db/seed_prices.py:154`: 400 days of synthetic random-walk data, rescaled so the last point equals the seeded price.
  - CMC is used only inside the sentiment engine, for momentum signals, and is never stored as a price.
- **Effect:** every price-derived number is frozen at seed time. It also contradicts the ML service (real Binance closes) and the live 24h changes CMC feeds into sentiment.
- **Scores:** nothing to fail, nothing to judge.
- **Better design:** a `market-worker` that every 1–5 minutes makes **one** batched `quotes/latest?id=…` call (1 credit for up to 100 ids; or CoinGecko).
  - It upserts `asset_market_data` with `fetched_at`.
  - It appends hourly `prices` with a unique (asset, hour) index and a roll-up/TTL.
  - The API exposes `is_stale`.
  - The sentiment engine reads market signals from this collection, so one component owns the quota and there is one source of truth.

### 7.2 B. Sentiment: collect → clean → VADER+FinBERT → aggregate → store → API → UI
- **Flow (VERIFIED):**
  - The scheduler waits 90 s, then runs every 15 minutes, gated by `claim_run` in Mongo.
  - 15 assets run in parallel. Each fetches **all 10 RSS feeds** (6 s timeout), matches keywords, applies a 72 h cut-off, and dedupes exact titles plus Jaccard ≥ 0.6 near-duplicates.
  - CMC is called 3 times per asset (quote, plus global and trending, cached 90 s with no lock).
  - Scoring blends VADER 0.35 with FinBERT 0.65, weights by recency (12 h half-life) and source trust, then combines 0.7 NLP with 0.3 CMC momentum.
  - Results are upserted into `sentiment` and appended to `sentiment_history` in the **separate `altinvest` DB**.
  - The API serves the cache if it is under 20 minutes old, otherwise runs the pipeline and waits up to 12 s.
- **Failure behaviour:**
  - RSS down: the last good reading is kept. Good.
  - FinBERT missing: VADER only, honestly labelled. Good.
  - Mongo down: a 30 s circuit breaker, served from memory. Good.
  - **CMC down or no key:** momentum becomes 0.5, which compresses every score 30% toward zero, yet the result is still "usable" for AAI and alerts (PL-15).
- **Quality issues:**
  - Weights are hand-set with no labelled evaluation set.
  - FinBERT is scored as ±confidence, discarding P(neutral).
  - 30% of "sentiment" is price momentum, which overlaps with the risk input.
  - A body mention of "bitcoin" counts like a headline: `relevance_score` is computed but never used.
  - Articles aren't persisted, so the same ones are re-scored every cycle.
  - `time.mktime` is applied to a UTC struct (wrong offset on dev hosts), and undated items are treated as "now".
- **Cost:**
  - 150 RSS requests per cycle (about 14k/day).
  - Up to 45 CMC calls per cycle, about 1.4k–4.3k/day, against roughly 333/day on the free tier (INFERRED plan limits). The quota is exhausted within days, after which every score silently degrades (PL-06).
  - `sentiment_history` grows by about 1,440 docs/day with no TTL or index (PL-08).
- **Better design:** a sentiment worker outside the API image.
  1. Fetch each feed once per cycle, using ETag/If-Modified-Since.
  2. Upsert articles by URL hash.
  3. Score only new articles in one FinBERT batch under a lock (ONNX/int8 optional).
  4. Aggregate per asset from the stored scores.
  5. Take momentum from the market worker.
  6. Downsample history with a TTL, and add an `(asset_id, timestamp)` index.

### 7.4 D. AAI: inputs → formula → schedule → consistency
- **Formula (VERIFIED, `aai_engine/aai.py:223`):** 0.40·pred + 0.30·sent + 0.30·risk.
  - pred = 50 + (ret30/20%)·50.
  - sent = normalised −1..1 → 0..100, shrunk toward 50 by confidence.
  - risk = `risk_score`, higher = safer.
  - Incomplete inputs give null; the scheduled refresh stores only complete scores.
- **Schedule:** +120 s, then every 30 minutes, with no lock and no input-age check (PL-05). Stale ML or seed inputs are rewritten with fresh timestamps.
- **Consistency (VERIFIED):**
  - Detail, Discover, Compare, Trending and Watchlist read the stored `aai_scores` row.
  - `/aai/{a}` always recomputes live.
  - `/intelligence` is meant to cache but never hits.
  - Live result: BTC 78.4 BUY (stored, seeded) vs 61.78 (`/aai/BTC`).
  - The UI uses only the stored path, so its pages agree with each other, but they display live sentiment next to an AAI computed from older sentiment.
- **Unit bug (PL-03, VERIFIED):**
  - `aai_controller.py:93,115` stores `sentiment_score` on a 0..100 scale.
  - Seed rows store −1..1 (`seed_data/assetDetail.json`: `"score": 0.31`).
  - The fallback readers (`market_controller._aai_fields:68`, `assets.py:111-117`, `alert_controller.py:113`, `portfolio_intelligence.py:66`, `discover.py:110`) treat the value as −1..1.
  - Whenever live sentiment is more than 60 minutes old, sentiment shows as "57.3" and alerts fire falsely.
- **Better design:** compute AAI in exactly one place (the worker) and store it with full provenance: input ids and timestamps, `sentiment_raw` and `sentiment_component` as separate fields, and `inputs_seeded`. Every endpoint reads that row. Return null with a reason when inputs are stale or seeded. Show no BUY/SELL unless the prediction comes from a real model.

### 7.5 E. Alerts: rule → evaluate → trigger → dedupe → notification → email
- **Flow (VERIFIED live):**
  - The evaluator starts at +60 s, then runs every 5 minutes.
  - Current values: price and NFT floor (seeded), AAI, risk, and live sentiment (falling back to the 0..100 stored value).
  - An alert fires when the value crosses between `last_observed_value` and the current value. It then moves to `triggered`, and that state change is the only cooldown until the user re-arms it.
  - On firing it inserts into `alert_triggers` and `notifications`, then sends the email synchronously (15 s SMTP timeout). Without SMTP the email is printed to stdout and the function returns False. There is no retry and no record of the failure.
  - Push is accepted as a channel and ignored.
- **Issues:**
  - Price alerts can't fire.
  - False sentiment fires (PL-03, PL-15).
  - Duplicates with more than one process (BE-04).
  - Emails can go to unverified addresses (BE-17).
- **Better design:**
  - Run evaluation in the worker under a lease.
  - Claim each alert atomically with `find_one_and_update({_id, status:"active", last_observed_value: prev})`.
  - Use a notification outbox with a retrying sender and an `email_status` field.
  - Evaluate on value changes (change streams on market and sentiment) instead of a 5-minute poll.

### 7.6 F. Portfolio snapshots + FX
- **Snapshots:** hourly, one upsert per user per UTC day, labelled `source:"live"`. Unpriced holdings are skipped. The upsert is idempotent, so multiple workers are harmless.
  - **But valuation uses frozen prices, so "live" history is a flat line.**
  - Earlier history is synthetic and backfilled, and its marker is dropped (BE-23).
- **FX:** Frankfurter, at startup and every 6 h, with a 15-minute retry. Validated and stored once per `as_of`. `/fx` returns 503 until the first fetch succeeds. Conversion happens client-side from USD, which is consistent. VERIFIED live: USD/INR 94.91.
- **Better design:** snapshot at a fixed UTC time from real prices with a `prices_as_of` field, and derive past quantities from transactions.

### 7.7 G. Trending, search, similar, NFT
- **Trending:** a z-score of the price move against the asset's own 30-day standard deviation, plus a volume ratio. The method is sound, but the inputs are frozen and synthetic.
- **Search:** an escaped regex over three collections. The `$text` index on insights goes unused.
- **Similar:** curated, or a min-max distance over seeded features.
- **NFT:** fully seeded with fictional collections mixed in. The seed duplicates rows on re-run. No NFT detail page.
- **Better design:** feed trending from the market worker; use Atlas Search; integrate an NFT provider (Reservoir or OpenSea) under Phase 8, or label the whole NFT area as demo.

## 8. Cross-cutting production readiness

- **Security, OWASP view:**
  - A01 access control: OK.
  - A02 crypto/secrets: **fail.** Public fallback JWT secret; credential in history; secrets in logs.
  - A04 insecure design: **fail.** Reusable reset token; unauthenticated expensive endpoints.

  - A06 vulnerable components: **fail.** 23 CVEs; unpinned dependencies.
  - A07 identification and authentication: partial. Enumeration; no MFA; JWT in localStorage.
  - A09 logging: **fail.** Tokens and URI logged; app loggers unconfigured.
  - A03 injection: OK.
- **Config and environment separation:** none.
  - `.env` serves dev, compose and Atlas at once.
  - There are two DB variable names.
  - There is no `APP_ENV`.
  - `get_db()` crashes when `MONGO_DB_NAME` is unset.
- **Production build and deploy:** none wired up. The frontend production image works but isn't used, and there is no backend production image.

- **Documentation:**

- **Legal and UX honesty:**
  - Asset Detail, Discover and Compare show STRONG BUY/SELL with no "not financial advice" disclaimer. Dashboard reports and analysis do have one.
  - Seeded and fabricated data is unlabelled.
  - Fake headlines are credited to real publishers.

## 10. Improvement list (works today, but should be built better)

| ID | Today | Better approach | Why it's better |
|---|---|---|---|
| IMP-01 | 7 daemon threads plus FinBERT in every API process | One `worker` container with APScheduler and a Mongo lease lock; a stateless API image without torch | Removes duplicate jobs, lets the API scale, a 9.7 GB image becomes about 300 MB, and failures are isolated |
| IMP-02 | Clock offsets between jobs (00:05 / 00:15, every 15 / 30 / 5 minutes) | Event chaining: ML refreshed → pull → AAI; market tick → alerts; sentiment saved → AAI. Change streams or a small queue | Fresher data, no wasted polls, no race windows |
| IMP-03 | Scattered `os.getenv` calls and accidental `.env` loading | One `pydantic-settings` object validated at startup, plus `APP_ENV` | Fails fast; separates environments |
| IMP-04 | Two Mongo clients, naive datetimes patched by hand | One shared `MongoClient(tz_aware=True)` with timeouts, one DB | Removes a class of timezone bugs (G-29) and 30 s hangs |
| IMP-05 | 24 h sliding JWT in localStorage | Short access token in memory, rotating hashed refresh token in an httpOnly cookie, reuse detection | Resists XSS theft and makes revocation enforceable |
| IMP-06 | Synchronous email inside request and scheduler threads | Outbox collection with a retrying sender | No timing leak, no lost emails, and a delivery status |
| IMP-07 | Ad-hoc `note` strings for provenance | A uniform `source / as_of / model_version / is_demo / status` on every number, plus a shared `<Score status>` component | Makes "fake but looks real" impossible by construction |
| IMP-08 | Hand-rolled `useAsync`, module caches, 4 event buses | TanStack Query (dedupe, staleTime, invalidation, visibility refetch, cleared on logout) | Fixes G-24 and G-40 and deletes about 300 lines |
| IMP-09 | Four separate fetch wrappers on the frontend | Everything through `apiFetch` | Tokens reach sentiment calls, and timeout handling lives in one place |
| IMP-10 | Absolute API URL baked into the frontend bundle | nginx proxies `/api` to the backend; `VITE_API_BASE_URL=/api` | One image for every environment, no CORS, and FE-03 goes away |
| IMP-11 | Universe endpoints run about 8 aggregations per request | 30–60 s TTL cache keyed without per-user flags | An order of magnitude less DB load |
| IMP-12 | Sentiment re-scores the same articles every cycle | Persist articles by hash and score only new ones; FinBERT P(pos)−P(neg); ONNX int8; a labelled evaluation set | Lower CPU, better calibration, measurable quality |
| IMP-13 | Five hand-written SVG chart components (most of the lint errors) | One chart primitive or a small library, sized from state instead of refs | Lint clean, less code |
| IMP-14 | Inline-style Sidebar and auth pages, duplicate toggles and modals, dead Tailwind | Small design-system components; pick Tailwind or plain CSS | Consistent and accessible |
| IMP-15 | Regex search | Atlas Search, or the existing text index | Fuzzy matching, uses an index |
| IMP-16 | No error tracking | Sentry (frontend boundary and `apiFetch`; backend middleware); structured JSON logs; `/health/jobs` | Problems become visible in production |

## 11. Recommended roadmap

Phases are ordered by dependency. Items inside a phase can run in parallel.

**Phase 0: stop the bleeding (2–3 days, no dependencies)**
- **Credentials:** G-05 (rotate and confirm the Atlas password, add gitleaks), G-03 (JWT fail-fast), G-04 (compose uses local Mongo by default).
- **Leaks and auth:** G-10 (redact logs; no printed links outside dev), G-08 (single-use reset that revokes sessions), G-09 (lock the refresh endpoints), G-14 (delete cascade), G-16 (no demo user outside dev), G-31 (CORS and headers).
- **Dependencies:** G-17 (pin and upgrade PyJWT and pymongo).

**Phase 1: tell the truth about data (1 week; needed before Phase 2's UI work)**
- **Provenance:** IMP-07 (fields in every payload and a UI badge).
- **Remove or label fabricated data:** G-07 (hide seeded forecasts and signals), G-19 (insights), G-39 (fake ticker and placeholder numbers), G-36 (mock risk), G-37 and G-38 (signal labels, disclaimer).
- **Fix wrong numbers:** G-12 (sentiment scale plus migration), G-28 (risk polarity), G-20 and G-46 (AAI input age and frozen rows).

**Phase 2: architecture (1–2 weeks; depends on Phase 0)**
- **Configuration and storage:** IMP-03 settings and G-18 (one DB, `APP_ENV`); IMP-04 one client with timeouts (G-26, G-29).
- **Worker:** IMP-01 worker container with a lease (G-13, G-30, G-44 heartbeats), including the alert atomic claim and the outbox (IMP-06).

**Phase 3: real data (1–2 weeks; depends on Phase 2's worker)**
- **Market data:** G-02 catalogue bootstrap; G-01 market worker with batched quotes; switch sentiment momentum to it (G-21, G-43).
- **Downstream jobs:** snapshots from real prices (G-47); trending from live data; G-22 history TTL and indexes.
- **Follow-on effects:** price alerts start working; Detail stops contradicting ML.

**Phase 4: product completeness (1 week; can overlap with Phase 3)**
- **Onboarding and settings:** G-06 onboarding persistence and gate; G-23 notification preferences honoured, or hidden; Push removed.
- **Frontend fixes:** G-24 and G-25 (useAsync and poller, best done via IMP-08 TanStack Query); G-40 over-fetching.
- **Accounts:** G-34 verification gating; G-15 enumeration; G-35 trade races; G-49 server export.

**Phase 5: production deployment and quality gates (1 week; depends on Phases 0 and 2)**
- **Deployment:** G-11 production compose with nginx `/api` proxy (IMP-10), non-root containers, healthchecks, Mongo auth, log rotation.
- **CI and tests:** G-27 CI (lint, tests, pip-audit, image build); fix the 58 ESLint errors; backend auth, ownership and alert suite; frontend Vitest; Playwright smoke test of the full journey.
- **Ops:** G-48 docs; backups for the (now single) DB.

**Phase 6: hardening and expansion (ongoing)**
- **Frontend:** G-41 responsive and accessibility work; G-42 code splitting.
- **Backend:** G-32 rate limiter; IMP-05 cookie refresh tokens; IMP-11 caching; IMP-12 sentiment quality.
- **ML:** G-45 PLAN_NEXT A1–A6; real models beyond the baseline; D1 NFT Phase 8 (real NFT data provider) or label NFTs as demo.

**Exit criteria for "production-ready":**
- No P0 or P1 findings open.
- Every number in the UI has `source` and `as_of`.
- A fresh `docker compose -f docker-compose.prod.yml up` produces a working, non-empty app with live prices.
- CI is green on lint, tests and pip-audit.
- The full journey in §3 passes as an automated Playwright run.

### 12.4 What could not be verified, and why
- **Browser UI rendering.** No browser tool was available. Layout, responsiveness (FE-17) and visual states come from code traces plus HTTP and bundle checks.
- **Live CMC data and quota behaviour.** `CMC_API_KEY` was deliberately not passed to the local stack. PL-06 plan limits are INFERRED.
- **Real SMTP delivery and SMTP-timing enumeration.** SMTP had to stay unset.
- **Whether the leaked Atlas password (58649d2) is still valid.** Connecting to Atlas was forbidden. It is known only that it differs from the current `.env` password.
- **24 h token expiry and the 30-day session cap in real time.** An expired *verification* token was tested by forging one with the local audit secret.
- **Multi-worker duplication.** Inferred from code (no lock, no status precondition). Not run with `--workers 2`.
- **ML contract tests against real data.** 12 tests were skipped because `ml/data/raw` is not on this host. ML did fetch real data inside the live container.
- **Cold image build time.** It would have required purging the user's shared 11 GB BuildKit cache.
- **NFT holding add/edit/delete live.** Skipped for time; list and validation were checked.
- **Sentiment model accuracy.** There is no labelled dataset to measure it against.

**Fixtures the audit itself wrote:** local container only, destroyed afterwards. They were the `seed_all.py` run, one inserted notification (for the ownership test), and the BTC price temporarily set to 85,000 and then restored (to make an alert fire). Nothing was written to Atlas or to any project file other than this report.
